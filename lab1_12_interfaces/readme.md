# Принципы SOLID

## 1. S — Single Responsibility Principle (Принцип единственной ответственности)
Суть: У класса должна быть только одна причина для изменения. Другими словами, класс должен отвечать за одну задачу.

Пример нарушения: Класс User хранит данные пользователя, отправляет email и сохраняет в базу. Если изменится способ отправки почты, придётся менять класс, что затрагивает и другие его функции.

Как правильно: Разделить на User (данные), UserRepository (сохранение), EmailService (отправка).


## 2. O — Open-Closed Principle (Принцип открытости/закрытости)
Суть: Программные сущности (классы, модули, функции) должны быть открыты для расширения, но закрыты для изменения. Новое поведение добавляется без изменения существующего кода.

Пример нарушения: Есть класс AreaCalculator, который считает площадь круга и квадрата через if-else. При добавлении треугольника придётся менять метод.

Как правильно: Создать интерфейс Shape с методом area(), реализовать его для каждой фигуры. AreaCalculator просто вызывает shape.area() — новые фигуры добавляются без правки калькулятора.

## 3. L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков)
Суть: Объекты подклассов должны заменять объекты базового класса без нарушения работы программы. Наследник не должен требовать больше, чем родитель, и не должен давать меньше.

Пример нарушения: Базовый класс Bird с методом fly(). Подкласс Penguin наследует Bird, но не умеет летать — приходится бросать исключение или оставлять пустой метод. Это ломает ожидания.

Как правильно: Выделить интерфейсы FlyingBird и NonFlyingBird или не делать fly() в базовом классе.

## 4. I — Interface Segregation Principle (Принцип разделения интерфейсов)
Суть: Клиенты не должны зависеть от интерфейсов, которые они не используют. Лучше много маленьких специализированных интерфейсов, чем один «толстый».

Пример нарушения: Интерфейс Worker с методами work(), eat(), sleep(). Класс Robot вынужден реализовывать eat() и sleep(), хотя они ему не нужны.

Как правильно: Разделить на Workable, Eatable, Sleepable. Робот реализует только Workable.

## 5. D — Dependency Inversion Principle (Принцип инверсии зависимостей)
Суть: Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций. Абстракции не должны зависеть от деталей; детали зависят от абстракций.

Пример нарушения: Класс OrderService напрямую создаёт MySQLDatabase и вызывает его методы. Если заменить БД на PostgreSQL, придётся менять OrderService.

Как правильно: Ввести интерфейс Database и передавать его в OrderService через конструктор. MySQLDatabase и PostgreSQLDatabase реализуют этот интерфейс — OrderService зависит от абстракции.
